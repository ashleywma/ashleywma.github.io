EECS 498 (Search Engines)

University of Michigan · Winter 2026

One semester-long project: build a working web search engine from scratch in C++ — no search libraries, no STL containers, no third-party HTTP or HTML stack. Six of us built it end to end and shipped it on a 25-machine AWS cluster. We called it Twoogle. This page is a high-level write-up of the system.

Source on GitHub

Scale it reached

  • cluster: 25 AWS EC2 i7i.2xlarge nodes (8 vCPU, 64 GB RAM each) on ephemeral NVMe SSD, sharded by hashed domain so inlinks and anchor text stay on one machine
  • crawl: 244,115,911 URLs in about four hours (~50M/hr), 39 crawler threads per machine, from a hand-built 312-link seed list
  • corpus: 652.23 GB of parsed documents plus 2,152.67 GB of anchor data
  • index: 200,484,475 pages, 333.8 billion tokens (~400 million unique), 6,137 chunks averaging ~250 MB, 1,481.87 GB — built in 20–25 minutes
  • on disk: 2,151.64 GB total — index plus the parsed HTML/PDF kept for snippets
  • query: ~300 ms average (50 ms – 1.5 s observed), fanned out from one frontend node to 24 solver shards plus a dedicated Wikipedia node
  • codebase: ~51k lines of C++, of which I wrote about 7.6k (~15%)

What I worked on

Most components were owned by pairs; the query-side language work turned out to be cleaner as a solo task, so I took it. I wrote the query compiler, the frontend, lemmatization, URL parsing, and spellcheck, plus a large share of our hand-rolled standard library (string, vector, hash table) that everything else was built on.

Query compiler

Tokenize → parse tree → ISR tree. Full query language: phrases, grouping, NOT, AND (explicit and implicit), OR, and fielded decorators for title, header, body, anchor, and URL.

URL parsing

Split URLs on separators, then word-break unknown segments against a merged dictionary (open-source word list unioned with the top 40k English words and 46.5k proper nouns) using O(n²) DP per chunk, emitting tokens and ranking signals.

Spellcheck & lemmatization

Length-bucketed dictionaries searched from n−2 to n+2, capped Levenshtein distance with early exit, ties broken by corpus popularity then lexicographically. Lemmatizer folds word variants to a common base at parse time to improve recall.

Frontend & lib

Search client and results rendering (title, description, URL fallback, truncation, spelling suggestions), and the from-scratch container library the whole engine depends on.

System

Crawler & frontier

What it does. The frontier holds every URL we discover, scored on heuristics like slash depth, seed-list distance, and query-parameter count, then bucketed into five priority tiers plus a dedicated bucket for seed-list links and seed-list hostnames. A bloom filter deduplicates fetches. Popping drains buckets in priority order but randomly within a bucket, which keeps host diversity high.

Politeness. A DNS pool resolves hosts, a robots pool fetches and caches robots.txt behind an in-flight table, and a fetch scheduler leases jobs to fetch threads while enforcing per-domain cooldowns, strikes, retries, and 429/timeout backoff.

What broke. After 20–30 minutes nearly every fresh URL belonged to a delayed host, so fetch threads starved. We were being too polite. Cycling those domains back through the frontier raised our 429 rate but restored domain diversity and kept throughput up.

Parsers — HTML, PDF, URL

HTML. Built on top of the course homework parser, then extended: a whitelist for tokens that legitimately contain punctuation (C++, .NET, Node.js), a blacklist for slurs and spam, lemmatization of stripped tokens, and trimming of alphanumeric runs past 55 characters as spam (the longest English word is 45; the extra bytes cover multi-byte UTF-8). Tokens are decorated by position — @ for title, $ for anchor — so the constraint solver can evaluate fields separately. We read <html lang="en"> to drop non-English pages and <meta> for descriptions and viewport.

PDF. PDFium extracts text as UTF-16, we convert to UTF-8 and feed it through the same parser object. The fiddly part was outbound links, since many PDF links point back into the same document.

URL. Mine — see above. Splitting on separators gets you most of the way, but real URLs are full of run-together words, so unmatched segments go through a dictionary word-break before being emitted as tokens.

Index & tiering

Layout. Each chunk — 6,137 of them, averaging about 250 MB — holds per-page metadata (URL, title, description), two hash blobs — one for body text, one for anchor text — and three posting-list sections: EndDoc, body, anchor. Positions are stored as variable-byte encoded deltas. Metadata and hash blobs are serialized at the head of the file so readers in the constraint solver can deserialize cheaply.

Tiering. Chunks are grouped by static rank so queries start in the highest-quality tier and only fall through if they can't fill top-K. Cutoffs live in a config file, so retuning doesn't mean recompiling the builder. Static rank is a uint8_t, 0–255. Our first build scored and sorted every URL in memory before assigning workers; switching to a streaming per-worker queue cut hours off build time.

Query compiler & constraint solver

Pipeline. The raw query string is compiled into a parse tree and then into an ISR tree of implicit ANDs. Every solver node carries its own compiler instance, so the frontend ships the query as a plain string and each shard compiles it locally.

Language. Phrases with "...", grouping with parentheses, ~ for NOT, &/&& or adjacency for AND, |/|| for OR at lowest precedence, and field decorators: @ title, ^ header, * body, $ anchor, % URL.

Performance. The solver orders ISRAnd and ISRPhrase to seek the rarest term first — leading with a stop word means seeking and skipping constantly. We also sized machines for RAM specifically so index chunks stay resident, since disk seeks would have dominated everything else.

Ranking — static and dynamic

Static, at index time. Computing this during the crawl would have made iteration hopeless (a crawl took four hours; an index build takes 25 minutes), and computing it at query time would cost latency for something knowable in advance. So parse-time document features go straight into the index. Boosts come from an accessibility score (alt text, viewport, description), link density (anchor tokens ÷ total tokens, sweet spot ~0.3–0.5), token-bytes ÷ HTML-bytes (~0.2–0.35), stop-word ratio (~0.3), and digit ratio (~0.15–0.2), each weighted by threshold or bell curve. Deductions come from unlabeled form fields, spam strings, deprecated tags, and <br> spam. Ratios were hand-tuned on 20–30 links and validated on a 5,000-URL crawl.

Dynamic, at query time. A Ranker prepares each query once, flattening the ISR tree into slots and groups so we never re-walk the tree per matched document. The final score is a linear combination of span scoring (a sliding window over sorted term positions, scored on coverage, compactness, order, phrase proximity, and earliness), query-term matching against title/URL/description with exact-match boosts, anchor evidence weighted by distinct sources and hosts, and a fielded BM25-style lexical score with field multipliers.

What we learned. Anchor-text-only scoring was our first approach and it worked surprisingly well — but anchor text is exactly what Google bombs exploit, so it can't stand alone. Separating Meh from Good pages was also genuinely hard: Wikipedia sometimes scored 150 while worse pages hit 200.

Serving & crash handling

Serving. Clients POST to a frontend node, which fans out to 24 solver nodes over a /search endpoint and merges top-K results before responding. Index chunks are assigned by chunk number mod 24 — the 25th node serves Wikipedia exclusively.

Crawler recovery. Checkpoints every five minutes with a write-to-temp-then-rename pattern and rotated backups, capturing the bloom filter, scheduler queues with per-domain rate state, in-flight jobs, peer outbound queues, and anchor queues. SIGINT closes worker queues and checkpoints before exiting. A supervisor restarts on failure and forces a restart above 50 GB resident to avoid OOM kills.

Everything else. The index builder is deterministic and finishes in under half an hour, so a failed build just reruns from scratch. The ranker is single-threaded per query with parallelism at the cluster level. The query server logs and survives accept and thread-creation failures but has no retry or circuit breaker — a dead backend fails that query.
